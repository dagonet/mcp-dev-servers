## 1. Version

**0.3.0.** Manifest schema changes shape (`files[*]` loses every v2 hash field, gains
`ownership`), and the status enum drops `CONFLICT`, `AUTO_UPDATE`, `PROJECT_CUSTOM`,
`UP_TO_DATE` for v3 manifests. Consumers keying on those names break, so minor bump under
0.x semver, same reasoning as 0.2.0. `requires_server: ">=0.3.0"`.

## 2. What the server cannot do as specified, or would do differently

### 2.1 Manifest v3 example is missing fields the server cannot work without

§6 shows `manifest_version`, `template_version`, `variant`, `requires_server`, `files`.
The server also needs:

- `templateRepo` — the only way it locates the template tree (`_get_template_dir`).
  Override args exist on `template_compute_status`, but nothing else has them.
- `placeholders` — every template hash is computed **after** placeholder replacement
  (`_apply_placeholders`), and `template` × `LOCAL_EDITED` is "project file ≠ replaced
  template at sync". Without placeholders every consumer file reads as LOCAL_EDITED.
- `template_commit` (a SHA) alongside `template_version` (a tag) — the migration base and
  the existing `three_way` base are reconstructed with `git show <sha>:<path>`. A tag works
  too, but a v2 manifest has only `lastSynced` (SHA), never `template_version`. See 2.4.

Agreed: v3 keeps `variant`, `templateRepo`, `placeholders`, and `template_commit` (SHA)
beside `template_version` (tag). The server reads `lastSynced` as an alias of
`template_commit` so a v2→v3 migration and any half-migrated manifest still resolve.

### 2.2 Hash format

§6 writes `"hash": "sha256:…"`. Server stores bare 64-hex today and `template_finalize_sync`
validates that. Proposal: v3 entries write the `sha256:` prefix, the reader accepts both.
One hash per `template` entry is sufficient: it is the replaced-template hash at sync.
`TEMPLATE_UPDATED` = current replaced template ≠ hash; `LOCAL_EDITED` = project file ≠ hash;
both true → `LOCAL_EDITED` wins (the action is the same overwrite, plus the diff). `once`
entries carry no hash (never diffed). Confirm the precedence rule.

### 2.3 The ownership table format must be fixed now, not "in the plan"

§6 defers `templates/OWNERSHIP or equivalent` to the toolkit plan. The server reads it —
`new_template_files` has to know the class of a path that is **not yet in the manifest**,
and the migration has to classify every file it rewrites. Proposal, server-side contract:

- Path: `templates/ownership.json` at the toolkit repo root (variant-independent, one file).
- Shape: `{"rules": [{"pattern": "hooks/**", "ownership": "template"}, ...]}`, first match
  wins, `pathlib.PurePosixPath.match`-style globs with `**`, paths relative to the variant
  directory (root-tracked `hooks/**` resolve as today).
- No match → the server reports the path under a new `unclassified_template_files` list
  and **does not** apply it. That is the server half of "a file with no class is a red gate".
- Optional per-rule `target` for the rename case: `{"pattern": "gitignore",
  "ownership": "once", "target": ".gitignore"}`. Today `_template_file_path` and `pp / rel`
  assume the same relative path on both sides; `gitignore` → `.gitignore` needs the
  mapping. The manifest key is the **project** path.

### 2.4 Migration base: v2 manifests have no `template_version`

§7 step 2 diffs against "the template `CLAUDE.md` at the consumer's held version (the v2
manifest's `template_version`, fetched by tag)". The server never wrote that field; v2 has
`lastSynced` = commit SHA of the template repo at the last sync (may be `"unknown"` or
empty on some consumers). Proposal:

- Base = `git show {lastSynced}:{template path of CLAUDE.md}` (the existing
  `_git_show_file` path, UTF-8 safe since #11).
- If `lastSynced` is missing or does not resolve: emit **no** hunk section, add a warning
  `migration_base_unavailable`, and still write the region content. Never diff against the
  current template — those hunks would be the v3.1 rewrite, not the consumer's edits.
- The `project.md` header comment records the base so a reader knows what the fenced
  hunks are relative to:
  `<!-- template-sync: project-owned; migrated from CLAUDE.md at v3.1.0; migration-base: <sha> | unavailable -->`

### 2.5 Migration must be an explicit tool, not a side effect of load

§7 says migration runs "when the server meets a v2 manifest — before any other step".
`template_load_manifest` is read-only today (the v1→v2 migration only mutates the returned
JSON; finalize persists). A migration that writes `project.md`, rewrites the manifest and
touches `CLAUDE.md` inside a load call is a side effect the skill cannot back out of.
Proposal:

- `template_load_manifest` returns `manifest_version`, `server_version`,
  `migration_required: true|false`, and refuses (`valid: false`, named reason) when
  `requires_server` is not satisfied.
- New tool `template_migrate_manifest(project_path, backup_dir)` performs §7 steps 1–5,
  copies the pre-migration `CLAUDE.md` and manifest into `backup_dir` first, and returns
  the written `project.md` content, the hunk count, and the backup paths. Idempotent via
  the marker line and the `manifest_version` check exactly as §7.5.
- The skill calls it at step 1 when `migration_required` is true. Nothing else in the
  server reads a v2 manifest differently than today.

### 2.6 "An old server refuses at step 1 with a named reason" is not true for 0.2.1

0.2.1 does not know `requires_server`. Against a v3 manifest it either fails
`Missing required field` (if `templateRepo`/`placeholders` are dropped — accidental, not
named) or, if 2.1 is adopted, loads it and reads every entry as "no baseline" (conservative
CONFLICT, no data loss, but not a refusal). The refusal must live on the **skill** side:
`server_version` absent from the load response ⇒ server < 0.3.0 ⇒ stop with the named
reason. That is what makes the penumbra `server_version` item load-bearing, not cosmetic.

### 2.7 Who writes the LOCAL_EDITED diff

§7 puts "write diff to the step-2b backup dir" under server behaviour. The server has no
notion of the backup dir today. Proposal: `template_apply_file` gains `backup_dir: str = ""`.
For a `template` entry whose current project content ≠ hash it writes
`<backup_dir>/<rel>.pre-sync` (the full pre-image) and `<backup_dir>/<rel>.diff`, then
overwrites. If `backup_dir` is empty in that state the call is refused with a named error —
overwriting a local edit without the backup is the data loss this spec exists to remove.
`template_compute_status` returns the diff inline too (`local_diff`) so the report can show
it without a second call.

### 2.8 `source="skip"` / keep-mine has no v3 meaning

§5a: no softer class. For a v3 manifest `template_apply_file(source="skip")` on a
`template` entry is refused with a named error; `source="provided"` stays (the skill still
needs it for placeholder-filled content). Existing v2 keep-mine entries migrate to
`template` and are overwritten on the first v3 sync with their diff saved — that is what
§5a asks for, stating it in §11 would avoid surprise.

### 2.9 PROJECT_CONTEXT key audit

Feasible inside `template_compute_status`: for `once` entries whose ownership rule carries
`"audit": "keys"`, parse `^\*\*(.+?)\*\*:\s*(.*)$` on both sides, report
`missing_keys` and `placeholder_keys` (value matches `\{\{.*\}\}`). Never writes. Keeping
the audit opt-in per rule avoids parsing `project.md` / `PROJECT_STATE.md` for keys they do
not have.

### 2.10 Unknown top-level manifest keys (open-brain question)

**Preserve and report.** `template_finalize_sync` and the v3 migration keep every top-level
key they do not own and list them in `unknown_keys` in the response. Rationale: the
toolkit has stamped keys the server never read (`deletedAcknowledged`), and silently
dropping them hides the mistake; silently keeping them hides it too. Reporting makes a
stale stamp visible in the sync report every time. The v3 migration drops the **known** v2
per-file fields (`templateHash`, `templateRawHash`, `localHash`, `locallyModified`,
`localPartHash`, `templatePartHashAtSync`, `resolution`) — those are not unknown, they are
superseded.

### 2.11 Penumbra items

- `template_get_diff(diff_type="unified")`: accept as an alias of `full`. The field stays
  `unified_diff` — every diff_type already returns unified format, so the name is right and
  the mismatch was the parameter, not the field.
- `template_load_manifest` returns `server_version` (from `__version__`). See 2.6 for why it
  is the version gate, not just a report line.

## 5. Consumer challenge round — batch 1 (MM-Agent @ 86561fe), server answers

### 5a. Key audit: three lists + deprecated — accepted, one simplification

Rule shape: `{"pattern":"PROJECT_CONTEXT.md","ownership":"once","audit":"keys",
"required_keys":["Protected branches","Gate","Test"],
"deprecated_keys":{"Gate Command":"Gate","Test Command":"Test"}}`.
Report: `missing_required` (in `required_keys`, absent from project),
`optional_absent` (in the template, absent from project, not required),
`placeholder_keys` (present, value matches `\{\{.*\}\}`),
`deprecated_keys` (present in project, listed in the map; the value names the replacement).
No `optional_keys` list — every template key not in `required_keys` is optional, so the
two lists cannot disagree with the template. Keys present in the project but not in the
template are ignored. Key names are compared without the `**…**:` decoration.

### 5b. Orphans — accepted, defined by the ownership rules, no opt-in

`orphans`: files on disk that match a `template`-class rule in `ownership.json`, are in
no manifest entry, and are not shipped by the template (a shipped one is
`new_template_files`). One source of truth, no hard-coded directory list. A consumer
silences a path with an explicit `{"pattern":".claude/agents/local-*.md","ownership":
"project"}` rule — first match wins, so it must precede the broad rule. Informational
only: never read for hashing, never applied, never touched. Cost: one walk over the
directories the template-class patterns root at (`hooks`, `.claude/agents`,
`.claude/rules`) — tens of files, no opt-in. §4's sentence narrows to "never reads or
writes project files; lists orphans under template-class patterns".

### 5c. `redundant_project_file` — accepted, migration-only

In `template_migrate_manifest`, for every manifest entry dropped because its path is now
`project`-class (or unclassified) and the file is still on disk: compare the file with
`_apply_placeholders(git show <template_commit>:<template path>)`. Byte-identical ⇒
`redundant_project_file` with a delete suggestion. Base unavailable ⇒ skipped with the
same `migration_base_unavailable` warning. Never deletes. Not computed on later syncs —
the file is `project` by then and invisible by §4.

### 5d. `transitional_duplicates` — skill-side only, with one warning

The server has no semantics for it; `local_diff` carries everything the skill needs.
**Consequence to state in the ledger:** `settings.json` is `template` class, so a
deliberate local addition there is `LOCAL_EDITED` on **every** sync and is overwritten
each time, with the diff saved to `backup_dir`. No merge class exists by design (§5a).
The retirement condition must be met, or the addition moved into the template/variant,
**before** the first v3.1 sync — otherwise the consumer re-applies it from `.pre-sync`
after every sync. The server cannot soften this without a merge class.

## 6. Consumer challenge round — batch 2 (penumbra @ v3.0.3), server answers

### 6.1 Migration base path — confirmed

Base = `git show <sha>:<_template_file_path(manifest, "CLAUDE.md")>`, i.e.
`templates/<variant>/CLAUDE.md`; root-tracked paths (`hooks/**`) resolve at the repo root
exactly as today. Spec §7 step 2 wording is the toolkit's fix.

### 6.2 Base is placeholder-replaced before diffing — confirmed

`_apply_placeholders(base, manifest["placeholders"])`, then `_split_custom_region`, then
diff the template parts. Same rule as the hashes (2.1). An unreplaced base would report
every `{{…}}` as a local edit.

### 6.3 `template_version` derivation at finalize — accepted, one counter

Algorithm: candidates = `git tag --merged <template_commit> --sort=-v:refname`; for each,
compare `git rev-parse <tag>^{commit}:<path>` with `<template_commit>:<path>` (tree object
ids) for every tracked path; first tag with all equal wins. Never `git describe`. No
match, or the template repo is not a git checkout ⇒ `template_version: null` +
warning `untagged_template_tree`.
**Counter:** the tracked path list (`hooks scripts templates user-level-reference`) is
toolkit layout, not server knowledge — it goes into `ownership.json` as
`"tracked_paths": [...]`. Missing key ⇒ the server falls back to `templates/<variant>`
plus every root-tracked pattern prefix, and says so in a warning. Cost: tags × paths
`rev-parse` calls, dozens at most.

### 6.4 Base durability fallback — accepted

Order: `template_commit` (alias `lastSynced`) → `template_version^{commit}` (tree-identical
over tracked paths by construction) → `migration_base_unavailable`. Existence checked with
`git cat-file -e <sha>^{commit}`. The tag must be fetched locally; the skill's
`git fetch --tags` step is what makes the fallback reachable.

### 6.5 `dry_run` on `template_migrate_manifest` — accepted

`template_migrate_manifest(project_path, backup_dir="", dry_run=false)`. With `dry_run`
nothing is written and `backup_dir` may be empty; the response carries the would-be
`project.md` content, `hunk_count`, `migration_base`, `redundant_project_file`, warnings,
and the would-be v3 manifest. The write path returns the same fields plus the paths
written. §8's consumer check then runs on the live tree.

### 6.6 Classification scope — confirmed, stated precisely

`ownership.json` classifies **template-tree paths**: files under `templates/<variant>`
and the root-tracked patterns, hence `new_template_files`, and manifest entries (their
project path mapped back to the template path through `target`). A consumer-tree file
with no manifest entry is `project` whatever pattern it would match: never diffed, never
hashed, never swept by the finalize drop pass. It appears only in `orphans` (5b), and
only when it matches a template-class pattern — "first match wins" selects the rule for
a template path, it never classifies a consumer file.

## 7. Consumer challenge round — batch 3 (yutraffic, rust-tauri), key audit, server answers

### 7a. Resolved values and `template_default_changed` — accepted

For every key in `required_keys` the audit reports `value` (consumer), `template_value`
(current template, placeholder-replaced), `template_value_at_sync` (template at the held
base, same chain as 6.4), and two flags: `template_default_changed` =
`template_value ≠ template_value_at_sync`, and `consumer_holds_old_default` =
`value == template_value_at_sync` (the consumer never customised it, so the moved default
is probably wanted). Base unavailable ⇒ both flags omitted, one
`migration_base_unavailable`-style warning `audit_base_unavailable`. Values are compared
after whitespace normalisation; the audit never writes.

### 7b. Qualified keys and aliases — accepted

A template key `K` is present when the consumer holds exact `K`, a qualified form
matching `^K \(.+\)$` (`Build (desktop)` satisfies `Build`), or any name listed in the
rule's `"aliases": {"Build": ["Build (desktop)", "Build (mobile)"]}`. All matches are
reported under `matched_as` so 7a's `value` is unambiguous (first match resolves; the
rest are listed). Applies to required, optional and deprecated lookups alike.

### 7c. `template_notes_changed` — accepted, audited rules only

For a `once` rule with `"audit":"keys"`: diff the placeholder-replaced template at the
held base against the current template; hunks that touch no `**Key**:` line are reported
as `template_notes_changed` with the hunk text. Key-line hunks are already covered by
7a and `optional_absent`. Never applied. Restricted to audited rules — a `once` file
without an audit (PROJECT_STATE.md) is never diffed, by §7's definition of `once`.
Base unavailable ⇒ skipped under `audit_base_unavailable`.

### 7d. `project.md` byte size in the migrate response — accepted

`template_migrate_manifest` returns `project_md_bytes` for the written or would-be file.
Threshold and warning are skill-side; the server never fails on size — the file is
consumer-owned.

### 7e. Additional `once` files — nothing for the server

`VERIFICATION_PLAYBOOK.md`, `.gitattributes`, `.prettierrc`, `rustfmt.toml` are table
rows; the server honours the rule.

## 8. Consumer challenge round — batch 4 (yutraffic), normalisation

### 8a. What the server normalises today — measured from the code

- **BOM:** `_sha256` and `_read_file` strip a leading U+FEFF before hashing/comparing.
- **EOL:** `_read_file` is `Path.read_text(encoding="utf-8")` — universal-newline mode, so
  CRLF (and lone CR) become LF before anything is hashed. `_git_show_file` runs the
  subprocess with `text=True`, same translation on the reconstructed base.
- **Trailing newline:** not normalised. `a\n` and `a` differ.
- **Writes:** `_write_file_atomic` uses `newline=""` — template LF lands as LF, no BOM.

So `IDENTICAL` today means "identical after BOM strip and EOL folding", and after an
overwrite the file **is** byte-identical to the template (LF, no BOM). §8's sentence is
true post-apply; the pre-apply comparison is the normalised one.

### 8b. v3 — accepted: keep normalising, state it in §7, report `encoding_drift`

Classification keeps the 8a normalisation (a BOM or CRLF-only difference is never
`LOCAL_EDITED`). Per file the status carries `encoding_drift: []` or a subset of
`["bom", "crlf"]` — the project file has the flag and the template does not, or the
reverse — informational only. Cost: the server already reads the file; it reads bytes
once, checks `startswith(b"\xef\xbb\xbf")` and `b"\r\n" in data`, then decodes — no
second read. `once` files (`.prettierrc`, `rustfmt.toml`) keep their BOM forever, drift
just names it. Trailing-newline differences stay real differences.

## 9. Consumer challenge round — batch 5 (open-brain), server answers

### 9a. `gate_self_reference` — accepted, three places

Definition (after open-brain's addendum — **direct** self-reference only, edited or
not): a whitespace-separated token in the value of a `required_keys` key of an audited
`once` file that, as a project-relative path, is `template`-class by the ownership
rules (matching a rule directly, or via `template_path_for` for `target` renames). No
status condition: an unmodified template `run-gate.sh` behind `**Gate**:` is already
broken, since the toolkit's script reads that key and refuses to invoke itself. Tokens
that are not paths (branch names, `none`, `true`) never match a rule and are ignored.

- `template_compute_status` reports `gate_self_reference: [{key, path}]` at top level
  (a report tool cannot refuse) and `gate_unverified: true` whenever the audited file
  declares `**Gate**:` — "this sync did not execute it". The server never executes it.
- `template_apply_file` on such a path refuses before any write with
  `error: gate_self_reference` naming the key — the server-side guarantee.
- `template_migrate_manifest` refuses (write mode does not write; dry_run reports it)
  with the same error, and carries `gate_unverified` too.
The static check is honest about its reach: a wrapper at `scripts/gate.sh` that still
calls `hooks/run-gate.sh` passes it (open-brain's ARM A fixture is the negative test);
the skill's post-sync step tells the consumer to run the gate once.

### 9b. `region_was_seed` — accepted

In migration, the region body (normalised per 8a) is compared with the template's own
region body at the base. Identical ⇒ the body is omitted from `project.md` and
`region_was_seed: true` is reported. Base unavailable ⇒ the body is kept and
`region_was_seed: null` (cannot tell; the header already says `migration-base:
unavailable`).

### 9c. Skill-side deletion offer — nothing for the server.

## 12. Per-file unknown manifest keys (batch 8, open-brain) — accepted

Same policy as top-level: preserved and reported. `template_finalize_sync` merges every
key of the existing on-disk entry that is neither a v3 field (`hash`, `ownership`) nor a
named superseded v2 field (`templateHash`, `templateRawHash`, `localHash`,
`locallyModified`, `localPartHash`, `templatePartHashAtSync`, `resolution`) into the new
entry; `template_migrate_manifest` applies the same rule to each v2 entry. Both responses
carry `unknown_file_keys: [{path, keys}]`. `template_apply_file` keeps returning the
two-field entry — preservation happens at finalize from the on-disk manifest, so a
hand-assembled or tool-built `applied_files` list cannot drop an annotation. `reason` is
not superseded and survives.

## 13. `applied_files_path` and the consumed echo (batch 9, panoscribe) — accepted, 0.3.0

`template_finalize_sync(..., applied_files_path: str = "")` reads the applied-files array
from a local JSON file the skill writes from the tool results; when given, the inline
`applied_files` is ignored. An unreadable or non-array file is a named error and the
